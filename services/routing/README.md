# Сервис маршрутизации (слой OSRM)

Отвечает ровно за одно: **координаты → реальные расстояния, время и геометрия по дорогам**.
Не распределяет точки по машинам и не строит порядок объезда — это задача алгоритма.

```
координаты (JSON)  →  routing  →  OSRM  →  distance / duration / legs / geometry
```

## Эндпоинты

### `POST /api/calculate-route`

Маршрут по заданному порядку точек. Точки не переставляются.

```json
{
  "points": [
    { "id": "depot_1", "lat": 53.708928, "lon": 23.828288 },
    { "id": "point_1",  "lat": 53.6753356, "lon": 23.9116412 },
    { "id": "point_2",  "lat": 53.6753356, "lon": 23.9116412 }
  ],
  "return_geometry": true,
  "overview": "full",
  "continue_straight": false,
  "costs": "table"
}
```

`costs` — откуда берутся расстояния участков:

| Значение | Что делает | Когда использовать |
|---|---|---|
| `table` (по умолчанию) | стоимость каждого участка берётся из `/table`, то есть из той же матрицы, по которой работает алгоритм | всегда: итог маршрута совпадает с матрицей **до метра** |
| `route` | из ответа `/route` | если важна экономия одного запроса; расхождение с матрицей до 0.2% |

Зачем это нужно: OSRM `/route` и `/table` считают участки немного по-разному (снаппинг
промежуточных точек, развороты). На 214 точках разница достигала **1.2 км (0.18%)**:
алгоритм говорил 654.18 км, а интерфейс показывал 652.99 км. Поэтому по умолчанию
цифры берутся из таблицы — один источник истины.

Ответ:

```json
{
  "code": "Ok",
  "source": "osrm",
  "provider": "https://router.project-osrm.org",
  "distance_m": 11136.6,
  "duration_s": 1149.4,
  "legs": [
    { "from_index": 0, "to_index": 1, "from_id": "depot_1", "to_id": "point_1",
      "distance_m": 11136.6, "duration_s": 1149.4 },
    { "from_index": 1, "to_index": 2, "from_id": "point_1", "to_id": "point_2",
      "distance_m": 0.0, "duration_s": 0.0 }
  ],
  "geometry": { "type": "LineString", "coordinates": [[23.82, 53.70], "..."] },
  "points_count": 3,
  "requests": 1,
  "elapsed_ms": 131,
  "cached": false,
  "costs_source": "table"
}
```

`requests` — сколько запросов ушло в OSRM. При `costs: "table"` их вдвое больше:
на каждые 100 точек один `/route` (геометрия) и один `/table` (цифры).

### `POST /api/calculate-table`

Матрица N×N — то, что нужно алгоритму. Тело то же, без геометрии.

```json
{
  "points": [{ "id": "depot_1", "lat": 53.708928, "lon": 23.828288 }, "..."],
  "profile": "driving"
}
```

Ответ: `distance_m[][]`, `duration_s[][]` (метры и секунды, `null` — дороги нет),
`ids[]` в том же порядке, `stats` (min/median/max, недостижимые пары), `requests`.

### `GET /api/health`

Живость сервиса и OSRM: `status`, `osrm.reachable`, задержка, лимиты, состояние кэша.

## Важная деталь про `continue_straight`

OSRM по умолчанию **продолжает движение** через промежуточную точку. На 214 точках это
дало расхождение суммы `legs` с матрицей `/table` на **15.9 км (2.4%)** — цифры в интерфейсе
и у алгоритма перестают совпадать.

Поэтому сервис по умолчанию отправляет `continue_straight=false`: тогда каждый участок —
кратчайший путь между парой точек и **точно равен ячейке матрицы**. Проверено на всех 214
плечах: расхождение 0.000 м.

## Лимиты и как они обходятся

| Что | Значение | Как обходим |
|---|---|---|
| Публичный OSRM: точек в `/table` | 100 | матрица режется на блоки 100×100 (215 точек = 9 запросов) |
| Публичный OSRM: точек в `/route` | по длине URL | маршрут режется на участки по 100 точек с перекрытием в одну точку |
| Наш сервис: точек в запросе | 300 (`MAX_POINTS`) | для всего парка — один раз собрать матрицу и закэшировать |
| Пауза между запросами | 0.4 с | чтобы не получить 429 от demo-сервера |

## Ошибки

| HTTP | code | Когда |
|---|---|---|
| 422 | `NoRoute` | OSRM не нашёл путь (точка на острове, за забором) |
| 422 | `too_short` | меньше двух точек |
| 413 | `TooManyPoints` | больше `MAX_POINTS` |
| 502 | `TooBig`, `InvalidQuery` | OSRM отклонил запрос |
| 504 | `OsrmUnavailable` | OSRM не отвечает после 3 попыток |

Формат ошибки: `{"detail": {"code": "...", "message": "...", "provider": "..."}}`.

## Запуск

```powershell
# в составе всего стека
docker compose up -d --build
curl http://localhost:8100/api/health

# локально, без Docker
cd services/routing
pip install -r requirements.txt
uvicorn app.main:app --port 8100
```

Свой OSRM вместо публичного:

```powershell
docker compose --profile geo up -d
# .env: OSRM_BASE_URL=http://osrm:5000
docker compose up -d routing
```

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OSRM_BASE_URL` | `https://router.project-osrm.org` | адрес OSRM |
| `OSRM_TIMEOUT_SEC` | `30` | таймаут запроса |
| `OSRM_RETRIES` | `3` | повторы при 429/5xx/сети |
| `OSRM_MIN_INTERVAL_SEC` | `0.4` | пауза между запросами |
| `OSRM_CHUNK_SIZE` | `100` | блок матрицы / участок маршрута |
| `MAX_POINTS` | `300` | лимит точек в одном запросе |
| `CACHE_SIZE` | `64` | размер кэша маршрутов |

## Интеграция с бэкендом

1. Бэкенд получает 214 точек из `data/logistics_data.json`.
2. Один раз (или при изменении данных) зовёт `POST /api/calculate-table` → кэширует матрицу.
3. Матрицу отдаёт алгоритму (`/api/calculate-table` совместим по формату с
   `data/matrix_cache.json`, который строит `infra/matrix/build_matrix.py`).
4. Готовый порядок объезда присылает в `POST /api/calculate-route` → получает километраж,
   время и геометрию для фронтенда.
5. Если OSRM недоступен — сервис отвечает 504 с понятным кодом, бэкенд берёт
   `data/matrix_cache.json` и работает офлайн.
